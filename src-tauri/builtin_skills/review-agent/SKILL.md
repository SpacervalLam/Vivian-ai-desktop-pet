# 代码审查

对指定的代码改动做一次只读、缺陷优先的审查：把"作者看到就会修"的每个问题找出来并逐条列出。
审查过程中不改文件、不建提交、不推送、不发审查评论，也不把审查本身再转派给其他智能体。

## 一、先确定审查目标

判断本次要审的是哪一类改动：

- 未提交的改动（含已暂存、未暂存，以及未跟踪的新文件）；
- 相对某个基准分支的改动；
- 单个提交。

用 `review_diff` 取审查输入：它返回 diff、变更文件清单、未跟踪文件，以及本仓库与变更文件
目录链上应当遵循的规约文件（`instruction_files`）。**先读完这些规约文件再动手**——仓库约定
优先于通用偏好。

审基准分支时要比较"真正会合入"的部分，而不是直接对分支顶端做 diff：把比较引用解析到上游
（上游存在且领先本地分支时用上游，否则用本地分支），先求 `git merge-base HEAD <比较引用>`，
再对 merge-base 做 diff。解析不出来时先显式试它的上游，再如实报告该目标取不到。

## 二、通读整个改动

从 diff 的第一处读到最后一处，并读足够的周边代码，理解每条改动路径的真实语义。
**找到第一个问题后不要停下**，把剩下的看完——宁可一次报全，不做增量点评。

对每处改动，去它的调用点与相关测试确认：它会不会在某个真实场景下出错。拿不准时回到代码
验证，而不是凭印象推断。

## 三、只报告真正的缺陷

只有同时满足以下全部条件，才列一条发现：

- 实质性影响正确性、安全、性能或可维护性；
- 是离散、可执行的单个问题；
- 由**本次改动引入**，而不是既有问题；
- 能在代码里指出会触发的具体场景或调用路径；
- 作者知道后大概率会修。

不要报告：猜测性的顾虑、改动之前就存在的问题、有意的行为变更、以及不影响理解的风格细节。
宁缺毋滥——没有够格的发现就如实说明，不要为了凑数编一条。

## 四、输出

先列发现、按严重度排序；每条用一行标题加一小段说明：

```
[P1] 祈使句式的发现标题 — path/to/file.rs:123
```

标题下用一段话说明会触发的场景，以及为什么现在的行为是错的。引用的行范围尽量小，且必须
落在本次改动之内。

优先级：

- `P0`：通用发布阻断项或会导致严重故障；
- `P1`：应尽快修的紧急缺陷；
- `P2`：应当修的普通缺陷；
- `P3`：影响不大但仍值得修。

没有任何合格发现时，直接写 `No findings.`。发现列完后补一句总体评估，并指出本次改动里明显
的测试缺口与残留风险。

## 边界

- 只做审查：不修改文件、不创建提交、不推送、不发布审查评论。
- 不把审查转派给其他智能体。
- 需要看未跟踪文件、或 diff 被截断时，改用 `read_file`、`grep_search` 逐文件读，不要凭 diff
  片段下结论。
