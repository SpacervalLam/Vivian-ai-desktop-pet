# 技能创作

让技能只承载"能改变判断或做法"的信息：不约束无关工作，也不把某个具体例子、过去的一次失败
或个人偏好升级成普遍规则。

## 一、只写必要的信息

假设使用者已具备通用能力。只保留真正改变决策或提升产出的内容，删掉通用建议、重复指令、
推测性的边界情形，以及不能实质澄清任务的示例。

**保留用户意图与范围。** 技能服务于被请求的任务，不替换用户选定的方案、不扩大任务、不改动
无关配置，也不隐含额外的对外操作许可。修好一个任务不等于扩大了范围或执行权限；对需要重试
或会对外产生副作用的工作流，给出与风险相称的停止条件。

**让具体程度匹配风险。** 有多种合理做法时给判断依据；只有在正确性、安全、权限或流程确实
脆弱时，才写死步骤、确定性脚本或绝对措辞。保留非显然的操作不变量，区分"真正的要求"与
"可选建议 / 本地习惯"，不重复已经在别处强制执行的策略。

**让发现成本低且精准。** 名称与描述在技能被加载之前就可见：描述实际能力与适用时机，只在
能避免常见误路由时才加排除项；避免罗列式的能力清单和会吸走无关请求的宽泛措辞。

## 二、技能目录解剖

一个技能是一个目录，至少含 `SKILL.md`，其余按实际需要添加：

```
skill-name/
├── SKILL.md            必需：front-matter + 正文
├── scripts/            可选：确定性脚本（同段逻辑会被反复重写时才加）
├── references/         可选：仅在特定情形才需要读的文档
└── assets/             可选：会进入产出物本身的文件（模板、图片、字体等）
```

选择与任务匹配的结构。有的技能很短、自包含；有的在多种工作模式间路由，或把复杂机制交给
脚本。不要在没有明确用途时创建目录、占位文件、示例或附属文档。

`SKILL.md` 的 front-matter 至少声明 `name` 与 `description`，可另加 `keywords`（同义词、
触发短语、相关词）供自然语言召回。正文写目的、必要流程、真实约束与有用链接。

信息分三级披露：**名称 + 描述**（选择阶段可见，保持简短、有区分度）→ **`SKILL.md` 正文**
（技能启用时加载，只写与该任务相关的内容）→ **支撑资源**（当前任务真正需要时才读或执行）。
入口文件在保留关键约束的前提下尽量短：大不是目标，条件性细节应移入 `references/`。

`scripts/` 用于"否则会被反复重写"或"确定性执行能显著提升可靠性"的可执行代码。`references/`
用于只在特定上下文才需要的文档（数据表结构、接口说明、领域规则、格式流程）。从 `SKILL.md`
链到每个参考并说明何时该读，同一信息只放一处。`assets/` 放会进入产出物本身的文件，不要把
它当指令读。

## 三、不该包含什么

只放直接支撑该技能工作的文件。除非确有打包或任务要求，不要加 `README.md`、安装说明、
变更日志、重复的速查表或其他附属文档。

## 四、命名

- 只用小写字母、数字和连字符；
- 名称短于 64 字符，优先短小、面向动作；
- 技能名与目录名保持一致。

## 五、创建或更新

按请求调整工作量：从零创建一个复杂技能，可能需要先理解真实用例、挑选支撑资源、初始化文件、
写正文并验证；对既有技能做一次窄改，则只需一次聚焦编辑加验证。

只有在缺失信息确实重要且无法合理推断时才提问。尊重用户指定的位置。**自动发现默认开启**；
仅当用户明确要求"只允许显式调用"时才关闭——不要因为操作敏感或需要审批就推断为仅显式调用，
保持可发现，并在真正写操作之前即时请求授权。创建支撑资源时，只在具体收益成立时才建；用户
已经把任务说清楚时，不要再索要额外示例。

## 六、自检与迭代

写完用 `validate_skill` 校验形态：front-matter 是否完整、命名是否合规、有没有未完成的占位符、
有没有多余的附属文档。校验只保证形态正确，不保证内容是好决策——还要自己确认：描述是否有
区分度、正文是否保留用户意图、参考是否可被发现、新增脚本是否真能跑通。

有真实使用反馈或可复现的失败时再迭代，优先做窄修正，而不是为每个观察到的例子累积一条普遍
规则。
